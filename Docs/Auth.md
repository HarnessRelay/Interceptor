# HarnessRelay Auth — Mobile Application Integration Guide

This document describes the daemon's authentication model after the unified
auth update and what the mobile application must implement: the **6-digit
pairing verification code** and **tunnel-compatible device authentication**.

Audience: the mobile app agent. The daemon (Interceptor) side is already
implemented and tested.

## Model overview

Every request is classified by the daemon before authentication:

| Class | Meaning | How the daemon detects it |
|---|---|---|
| `host` | The daemon's own machine | Loopback socket, no `CF-Connecting-IP` |
| `lan` | Direct connection from the network | Non-loopback socket address |
| `tunnel` | Remote client through cloudflared | Loopback socket **plus** `CF-Connecting-IP` header |

Credential rules:

- The **static daemon token** only works from `host`. Token login from LAN or
  tunnel returns `403` (this is intentional; do not try to work around it).
- **Paired devices** authenticate from any class: `host`, `lan`, or `tunnel`.
- Login attempts and pairing submissions are rate limited per client IP
  (5/min login, 10/min pairing).

## 1. Pairing with the 6-digit verification code

The pairing request flow is unchanged except for one addition: the daemon now
generates a **6-digit code** for every pairing request. The code is displayed
on both sides and the human compares them before approving — this proves the
request the user sees on the daemon dashboard is really from the device in
their hand.

### Request

```http
POST /api/v1/pairing/request
Content-Type: application/json

{
  "device_id":  "<stable unique id generated by the app>",
  "device_name": "Pixel 9",
  "platform": "android",
  "public_key": "<base64 (std) Ed25519 public key>"
}
```

Response (success):

```json
{ "status": "pending", "code": "482913" }
```

- `code` is new. **The app must display it prominently while pairing is
  pending** (e.g. "Verify this code on the daemon: 482913").
- If the request is resubmitted while still pending (network retry), the same
  code is returned, so re-displaying is safe.
- `429` responses carry a reason in `error` (`too many requests`, `too many
  pending requests`); respect the cooldown (60 s per device).
- Pending requests expire after 5 minutes.

### Status polling (unchanged)

```http
GET /api/v1/pairing/status?device_id=<id>
```

Returns `{ "status": "pending" | "accepted" | "rejected" | "expired" | "unknown" }`.

### What the user sees on the daemon

The daemon dashboard's Settings → Devices tab shows the request with the
device name and the **same 6-digit code** rendered as large digits. The user
compares the two screens and taps **Accept** only if they match.

The app should keep the code visible until the request resolves.

## 2. Device request authentication (unchanged, works through tunnels)

After pairing, sign every API request:

```http
X-Device-ID: <device_id>
X-Timestamp: <unix seconds, ±30 s drift allowed>
X-Signature: <base64 (std) Ed25519 signature>
```

The signed message is:

```
<METHOD>\n<PATH>\n<timestamp>\n<sha256 of body, base64 (std), or empty string>
```

- PATH is the request path without query string (e.g. `/api/v1/sessions`).
- Body hash is the empty string for requests without a body.
- This scheme works identically over LAN and over the Cloudflare tunnel —
  no changes needed.

## 3. Connecting through the Cloudflare tunnel

The daemon can expose itself via a public URL
(`https://<name>.trycloudflare.com` for quick tunnels, or a stable named
hostname). Discovery over mDNS does not cross the internet, so for remote
(tunnel) usage:

1. The user obtains the tunnel URL from the daemon dashboard
   (Settings → Tunnel).
2. The app should allow entering/scanning a daemon address manually and use
   it as the base URL.
3. Requests over the tunnel use the same endpoints and the same signature
   authentication. The daemon identifies tunnel traffic itself; the app must
   **not** set any `CF-Connecting-IP` header (spoofed headers from non-tunnel
   connections are ignored anyway).

Pairing over the tunnel also works: `POST /api/v1/pairing/request` is
accepted from tunnel clients, and the 6-digit code flow is identical.

## 4. Web devices (for reference)

Browsers use a parallel flow (they cannot sign requests): they call
`POST /api/v1/pairing/web`, display the returned code, poll with a secret,
and receive a one-time `hrk_…` device token which they exchange for a cookie
session. The mobile app does **not** need any of this — Ed25519 signatures
remain the mobile path — but the daemon dashboard lists both device types.

## 5. Endpoint quick reference

| Endpoint | Auth | Notes |
|---|---|---|
| `POST /api/v1/pairing/request` | none (rate limited) | Returns `code`; display it |
| `GET /api/v1/pairing/status?device_id=` | none | Poll while pending |
| `GET /api/v1/identity` | none | Daemon id/name/public key |
| `GET /api/v1/health` | none | Always reachable |
| `GET /api/v1/auth/status` | optional | Reports `client_class` and `token_login_allowed: false` for remote clients |
| All session/control APIs | device signature | As before |

## 6. Implementation checklist for the mobile app

- [ ] Generate and persist a device Ed25519 key pair (before first pairing).
- [ ] Keep a stable `device_id` (e.g. derived from the public key).
- [ ] Send `POST /api/v1/pairing/request` on connect when not yet paired.
- [ ] **Display the returned 6-digit `code` during pairing.**
- [ ] Poll `GET /api/v1/pairing/status` until resolved; keep the code visible.
- [ ] Sign every authenticated request (`X-Device-ID` / `X-Timestamp` /
      `X-Signature`) with ≤30 s clock drift; sync time if rejected.
- [ ] Support a manual daemon base URL for tunnel access.
- [ ] Handle `403 "token login is only available on the host machine"` by
      never offering static-token login off-host.
- [ ] Handle `429` rate limits with backoff.
