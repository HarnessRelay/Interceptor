# Terminal Rendering

## Recommendation

Forward raw PTY bytes to the browser as the canonical Stage 1 rendering path and render them with [xterm.js](https://xtermjs.org/docs/). Use `@xterm/addon-fit` for browser-side sizing and keep backend terminal snapshots minimal until raw replay and reconnect behavior are proven.

## Reasoning

- The PTY stream is already the terminal protocol. Transforming it too early risks breaking TUIs.
- xterm.js is built for browser terminal emulation and has maintained addons for attach, fit, search, serialize, Unicode, web links, and WebGL rendering.
- Raw terminal fallback is required by `Context.md`; semantic adapters are optional.
- Browser rendering should mirror a real terminal: bytes out, key/paste bytes back in, resize rows/cols to backend.

## Alternatives Considered

| Alternative | Decision | Reason |
| --- | --- | --- |
| xterm.js | Choose | Mature, maintained, supports VT streams and input capture. |
| Plain `<pre>` output | Reject | Cannot handle cursor movement, alternate screen, colors, or full-screen redraws. |
| Backend HTML rendering | Reject for Stage 1 | Complex and risks diverging from terminal behavior. |
| Custom canvas renderer | Reject | Too much implementation risk and no benefit for first dashboard. |

## Raw Output Streaming

WebSocket `terminal.output` events should carry raw bytes encoded as base64 in JSON for Stage 1:

```json
{
  "type": "terminal.output",
  "session_id": "ses_123",
  "seq": 42,
  "ts": "2026-07-25T10:20:30.000Z",
  "data": {
    "encoding": "base64",
    "bytes": "G1szMm1PSxsWzBtDQo="
  }
}
```

Base64 keeps the event envelope JSON-only and avoids UTF-8 corruption. Later optimization may use binary WebSocket frames after the protocol is stable. Browsers support binary frames through `WebSocket.binaryType = "arraybuffer"` according to [MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/binaryType), but JSON-first is easier for debugging and schema tests.

Frontend decode path:

```ts
const bytes = Uint8Array.from(atob(event.data.bytes), c => c.charCodeAt(0));
term.write(bytes);
```

## Browser Input Mapping

Use xterm.js `onData` for keyboard input:

```ts
term.onData((data) => {
  api.post(`/api/v1/sessions/${id}/input`, {
    mode: "raw",
    data: btoa(data)
  });
});
```

Input endpoint rules:

- `mode: "raw"` means base64 bytes are written directly to PTY.
- `mode: "text"` is optional helper behavior that encodes UTF-8 text.
- Special keys should initially be generated by xterm.js, not by custom key mapping.
- Provide explicit backend helpers for interrupt/terminate rather than relying only on key bytes.

## Paste Handling

Recommendation:

- Allow paste into xterm.js, but route through the same input API.
- Add a size limit, recommended default `64 KiB` per input request.
- Add rate limits or backpressure for repeated paste requests.
- Audit that paste occurred with byte count, not full content by default.
- Preserve literal pasted bytes unless the frontend explicitly normalizes line endings.

Risk: pasted secrets may enter harness prompts and terminal history. Do not log input payloads by default.

## Resize Handling

Use `@xterm/addon-fit` to calculate terminal rows/cols from the container. xterm.js docs recommend debouncing resize calls so the PTY can respond before another resize.

Flow:

1. Browser observes terminal container with `ResizeObserver`.
2. Debounce, recommended `75ms`.
3. Run `fitAddon.fit()`.
4. Read `term.rows` and `term.cols`.
5. POST `/api/v1/sessions/{id}/resize`.
6. Backend calls `pty.Setsize`.

Do not infer rows/cols on the backend from pixels.

## Scrollback And History

Stage 1 should keep two separate concepts:

- Browser scrollback: xterm.js local buffer for the connected browser.
- Backend history: bounded raw PTY byte chunks for reconnect/replay/debug.

Default backend retention:

- Keep last `4 MiB` raw PTY bytes per session in storage or memory-backed ring buffer until SQLite history exists.
- Also keep per-event sequence numbers and timestamps.
- Truncate oldest chunks first.
- Record truncation with a `terminal.history_truncated` event or metadata flag.

Reasoning:

- `4 MiB` is enough for early reconnect/debug without unbounded growth.
- Raw bytes preserve ANSI state better than line logs.
- Browser scrollback alone is insufficient for reconnect.

## Minimal Snapshot Strategy

Stage 1 minimum:

- `GET /api/v1/sessions/{id}/snapshot` returns dimensions, latest sequence, history truncation flag, and recent raw byte chunks.
- Browser creates a fresh xterm.js instance, replays the chunks, then resumes live stream after `after_seq`.

Example:

```json
{
  "session_id": "ses_123",
  "rows": 40,
  "cols": 120,
  "latest_seq": 900,
  "history_truncated": false,
  "chunks": [
    { "seq": 890, "encoding": "base64", "bytes": "..." }
  ]
}
```

Do not build a full backend terminal screen emulator in Stage 1 unless replay proves inadequate. A later phase can add a real terminal state library or xterm serialize-based snapshots.

## Risks And Limitations

- Replaying raw chunks may not reconstruct screen state if history starts after important terminal setup sequences.
- Alternate-screen applications may appear odd after reconnect if the retained stream is incomplete.
- Base64 increases payload size by about one third.
- Slow clients must not block PTY reads; backend should drop/disconnect slow consumers after bounded buffering.

## Acceptance Criteria For Later Implementation

- Browser renders colored ANSI output correctly.
- Browser can interact with `/bin/sh`, prompts, arrows, Enter, Backspace, Tab, and Ctrl+C.
- Resize changes update xterm.js and backend PTY.
- Reconnect replays recent output and resumes live events without duplicate chaos.
- Full-screen redraw fake harness remains usable.
- Raw terminal remains available even when semantic events exist.

## Required Tests

- ANSI fake renders escape sequences through raw event replay.
- Input API writes exact bytes to fake harness.
- Paste larger than limit is rejected with clear error.
- Resize event is debounced on frontend and applied on backend.
- Snapshot returns bounded raw chunks and truncation metadata.
- WebSocket slow-consumer behavior does not block PTY reader.
