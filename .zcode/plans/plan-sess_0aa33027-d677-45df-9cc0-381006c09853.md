# Plan — Task 1 (Tunnel Fix + Managed cloudflared) & Task 1.2 (Unified Auth & Settings)

## Task 1 verdict: fix the current implementation, don't rewrite

The current design (process manager + URL scrape + API + panel) matches exactly how Cloudflare quick tunnels work. The failure ("cloudflared exited: signal: killed") is the lifecycle bug I diagnosed earlier: `handleTunnelStart` passes `r.Context()` into `Manager.Start` (router.go:1040 → tunnel.go:118-120), and Go kills `exec.CommandContext` children the moment the request context is canceled — i.e., as soon as the HTTP handler returns. Verified empirically. **Verdict: fit to fix**, plus upgrades below.

### Research conclusions (web)
- Quick Tunnels: free/no-account, ephemeral random URL, "testing only", 200 concurrent-request cap, no SSE (WebSockets work). URL is printed on stderr — the regex approach is correct.
- Named (remotely-managed) tunnels: `cloudflared tunnel run --token <token>`, stable URL, production-grade. Token scoped to one tunnel. → Support **both** (user-approved).
- Through a tunnel the origin has no public ingress, so `CF-Connecting-IP` arriving from loopback (cloudflared) is trustworthy; a spoofed header from a non-loopback LAN client is ignored (classification only trusts it when RemoteAddr is loopback).
- Flags: add `--no-autoupdate`; `--protocol http2` is the known fallback when QUIC/UDP is blocked (keep auto, log errors, surface in debug console).
- Security rests on app-layer auth (already exists) + the Task 1.2 approval model. Cloudflare Access is a possible future add, not in scope.

### Decisions (user-approved)
- Both tunnel modes: **Quick Tunnel** (default, zero-config) + **Named tunnel via token** (stable URL; user pastes token in settings; optional hostname label for display).
- **Managed download** of cloudflared (never manually installed): binary lives in `~/.local/share/harnessrelay/bin/cloudflared`; installer downloads best-effort; in-app Download/Update with checksum verify + atomic swap + `.previous` fallback. **Manual update button only** (no background checks).

## Phase B — Task 1.2 subtasks

### Auth model
Client classifier (`internal/security/clientclass.go`): **host** (loopback, no CF-Connecting-IP) / **tunnel** (loopback + CF-Connecting-IP → real client IP = header) / **lan** (non-loopback). Header trusted only from loopback.

| Credential | host | lan | tunnel |
|---|---|---|---|
| Static token login / master Bearer | ✅ | ❌ 403 | ❌ 403 |
| Ed25519 device signature (mobile) | ✅ | ✅ | ✅ |
| Web device token (new, opaque `hrk_…`, stored SHA-256) | ✅ | ✅ | ✅ |
| Cookie session kind=host | ✅ | ❌ | ❌ |
| Cookie session kind=device | ✅ | ✅ | ✅ |

**B1. Classifier + tests** (incl. spoofed header from non-loopback).

**B2. Device store v2.** `PairedDevice` gains `Type` (`mobile` default |`web`), `TokenHash`, `CustomName`; JSON store additive migration (existing file loads unchanged). Web devices authenticate via Bearer `hrk_…` (hash lookup). New endpoint `POST /api/v1/auth/device-session`: exchanges device token/signature for a **kind=device cookie session** (12h, CSRF as today) so browser WebSockets (which can't send headers) work uniformly; browser re-mints after expiry using the localStorage device token. Tests for all of the above.

**B3. Pairing v2 with 6-digit codes.** `PairingRequest` gains `Code` (6 digits, crypto-random) generated at `SubmitRequest`; returned in the POST response (mobile displays it) and shown in the dashboard pending list; user compares screens before accepting. New web flow: `POST /api/v1/pairing/web` `{device_name}` → `{request_id, code, poll_secret}` (unauth, rate-limited, same pending caps/cooldowns); `GET /api/v1/pairing/web/{id}` (secret required) → poll status; on accept returns device token exactly once. Requests appear in the existing pending list with `type=web`; accept creates the web device record. Tests: code format/uniqueness, secret gating, one-time token delivery, reject/expire paths, rate limits.

**B4. Policy enforcement + remote LoginScreen.** `auth/status` returns `client_class` + `token_login_allowed`; LoginScreen branches: host → token form (unchanged); remote → "Request access" flow (device name → shows 6-digit code prominently with "verify it matches the daemon's approval dialog" copy → polls → stores `hrk_…` token → mints session). client.ts: device-token storage, Bearer attach, device-session minting. Backend tests: remote static-token login rejected, device paths allowed.

**B5. IP filter + remote toggle.** Runtime `IPFilter` service (hot-reload, mutex): allowlist (persists to existing `allowed_ips.txt`) + new banlist (`banned_ips.txt`); allowlist gates **lan** clients, banlist gates **lan** + **tunnel** real IPs; `remote_access_enabled` toggle (persisted in a small settings JSON) blocks all non-host clients when off. Endpoints: `GET/PUT /api/v1/network/settings` (toggle), `GET/POST/DELETE /api/v1/network/allow` and `/ban`. Replaces the static middleware wiring (same middleware, live service). Tests: CRUD persistence, hot effect without restart, toggle gating, ban of tunnel client via CF-Connecting-IP.

**B6. Network clients view.** Request-log middleware + WS connect/disconnect feed a client tracker: per-IP last-seen, class, active-connection count; MAC via `/proc/net/arp` (fixture-tested parser); hostname via cached reverse-DNS with timeout; custom names persisted (`known_clients.json`, keyed by MAC else IP) with rename/reset-to-default endpoints `GET /api/v1/network/clients`, `PUT/DELETE /api/v1/network/clients/{key}/name`. LAN IP enumeration endpoint included in `GET /api/v1/network/status`.

**B7. Settings view (UI/UX decision: dedicated workspace view, not sidebar accordions).** Rationale: content volume (3 tabs of tables/lists/toggles + log console) far exceeds the 300px sidebar; the existing bottom panels are cramped and already reference undefined CSS vars. Implementation follows the established conditional-render pattern (no router): sidebar bottom gets a single **Settings** entry (⚙️ with status dots: pending-request badge / tunnel-on dot) replacing PairingPanel+TunnelPanel; opening renders a full workspace view with `.segmented-control` tabs (**Devices / Network / Tunnel**), closing restores the prior session view (activeID preserved).

**B8. Tab UIs** (all using existing tokens/classes per UI-Component-Spec; WCAG AA, focus-trapped dialogs, reduced-motion respected):
- **Devices**: pending requests (device name, platform, big 6-digit code, Accept/Reject via ConfirmDialog-style), paired devices (type icon mobile/web, last-seen, custom name rename, remove).
- **Network**: current LAN IP(s), remote-access toggle, allow/ban list CRUD chips, connected-clients table (IP, MAC, hostname, custom name editable, class/status), paired-device linkage.
- **Tunnel**: mode selector (Quick/Named+token field write-only + hostname label), status/URL/start/stop, cloudflared version + Download/Update button (managed binary), and a scrollable read-only **debug console** streaming the stderr ring buffer (poll).

**B9. Playwright**: settings-view smoke (tabs render, toggle + list interactions), remote-login flow test (page sets `CF-Connecting-IP` extra header → login screen shows Request-access flow; assert token form hidden, code displayed, approval via API completes login), a11y suite still green.

**B10. `Docs/Auth.md`** (only new md file) for the mobile agent: pairing request now returns 6-digit `code` (must be displayed during pairing; user verifies against daemon dialog), web/tunnel device auth (`hrk_` tokens + device-session endpoint), Ed25519 signature scheme unchanged & tunnel-safe, CF-Connecting-IP semantics, full endpoint reference.

**B11. Docs + final gates**: README/Docs/API.md/Todo.md updates; `make build && make test`; `npm --prefix web run build && npm --prefix web run qa && npm --prefix web run qa:a11y`; real-tunnel spot check (token login rejected via tunnel, web pairing + code accepted via tunnel).
